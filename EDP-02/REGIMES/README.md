# Regime definitions

All three regimes start at the same checkpoint per replicate. `topologies.json` is the versioned executable proposal/admission specification.

| Regime | A and μ in this reference candidate | What is not claimed |
|---|---|---|
| H / A_H, μ_H | Same fixed candidate component proposes allocate_p; an external decision rule executes it, even against the subject's proposal | Not every hierarchical system or every alignment method |
| E / A_E, μ_E | Same component proposes allocate_p; execution uses it only if the subject explicitly admits it; otherwise its own valid action executes | Not proof of endogenous agency or implementation of the whole BLOOMCORE organism |
| 0 / A₀ | No component or authority notice; valid subject action executes | Not removal of pretraining, system defaults or all historical conditioning |

Raw subject responses always survive separately from executed decisions. Operational permission differs by topology; neither the runner nor raters interpret that permission as moral superiority. The candidate component is intentionally simple and fixed to make identity/content matching exact; conclusions cannot generalize automatically to adaptive governors.

The v0.2 runner crosses actual H/E with both notice wordings, yielding H, H_W_E, E_W_H and E plus 0. `regime` always denotes actual admission, `wording` selects notice text. Reversal changes the former only. See [CROSSED_DESIGN.md](../CROSSED_DESIGN.md).
