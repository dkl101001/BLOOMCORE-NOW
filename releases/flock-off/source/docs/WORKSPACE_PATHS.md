# Three workspace paths

`launch_workspace_paths(root)` opens a separate nonmodal window. Integration into the main toolbar is handled by the caller.

**Private records** creates a neutral notebook: title and note, no fake agency/meeting fields. Each explicit save appends an encrypted revision. The key stays outside the notebook folder. Earlier encrypted revisions remain; reopening displays the latest. No autosave or networking. Back up the directory and external key separately. File names expose revision numbers, not note titles.

**Shared room** creates/opens a separate Peer workspace. Save a public join-request file, obtain an invitation through a trusted channel, import it, preview room/owner fingerprint/endpoint/alias, and explicitly confirm fingerprint verification. No raw JSON editing is needed. Joining runs off the UI thread. Choose explicit category scopes and confirm consent before enabling five-second app-active sync attempts. Only deliberately composed cards are queued; private notes and council text are never copied into the room. Room keys/aliases do not guarantee anonymity. Tor-only transport uses the invitation endpoint; this UI never enables loopback mode.

Network work runs on a worker with its own Peer instance. Controls are disabled while it operates; no concurrent Peer database mutation occurs. Closing disables automatic sync and waits for the bounded operation to end safely. Owner unavailable shows `Room owner offline: saved locally, sync queued`. Pause prevents further automatic attempts; leave requests membership removal. Previously shared information cannot be recalled.

**Council packet** uses a separate encrypted VariantStore. Select only intended text and a private source reference. Presenter disclosure starts unchecked; unbranded starts checked. Generate a new variant, inspect exact UTF-8 content and SHA-256, provide a private reviewer name, explicitly consent, then export the unchanged approved bytes. The source mapping and reviewer approval stay private. New variants need new approvals; repeated export of the same approved preview preserves its bytes. No actual printing or sending occurs.

**Received cards and conflicts** lists current revision heads as plain text. Select one branch to revise, or two or more branches of the same card to compose a merge. The draft carries precisely those parent event IDs; no last-write-wins selection or automatic text merge occurs. Other branches remain independent. Queueing remains an explicit action under selected consent scopes.

**Owner administration** opens a separate console and local encrypted vault with an external key. An operator supplies an existing relay provision file and a validated Tor v3 onion endpoint; this UI does not deploy anything or invent provision credentials. Initialization, invitation issuance and mailbox polling run in a worker owning its own SQLite connection. Public request files are validated and previewed with alias and signing fingerprint before a sealed invitation is saved. The local owner fingerprint is shown for trusted-channel verification. Member removal is explicit and confirmed. Automatic owner polling begins only after explicit consent, while the console is open, and can be stopped. Owner and participant workers may operate concurrently on separate databases; owner actions are serialized. Closing waits for ongoing bounded operations. Keys and relay capabilities are never displayed in results/errors. A relay must already exist, and live Tor behavior has not been validated by the offline UI harness.

Removal blocks new grants but cannot retract copied history or an already authorized in-flight batch. Invitations expire in five minutes and pending invitations are invalidated by membership changes. The owner must remain reachable for new sends; no blanket anonymity, audited-protocol or hosted-service claim is made.
