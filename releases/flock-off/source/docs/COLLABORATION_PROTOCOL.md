# Collaboration protocol 1 — review candidate

This is a new application protocol using PyNaCl/libsodium sealed boxes and separate Ed25519 signing keys. It is not audited MLS, and makes no forward-secrecy, post-compromise-security or guaranteed-anonymity claim. Free text can identify its author. The owner knows membership. The relay sees opaque mailbox/room routing, timing and volume; Tor does not eliminate traffic correlation. A compromised local endpoint can read its local keys and plaintext.

Each room uses a distinct owner key and each peer workspace has distinct signing/encryption keys and alias. A sealed invitation pins the owner signing/encryption keys, onion endpoint, room, recipient mailbox and one-use join capability. The recipient previews the fingerprint and confirms the trusted delivery channel. A fingerprint displayed by an untrusted invitation is not independent authentication.

All signatures bind `FLOCKOFF-COLLAB-V1\0`, purpose, a NUL separator and canonical UTF-8 JSON bytes. JSON uses sorted keys, compact separators, no floats/NaN, duplicate keys, excessive nesting or oversized messages. Sealed encryption alone does not authenticate a sender; signed documents are inside the ciphertext.

Owner request: `schema, room, author, nonce, issued, action, data`, signed with purpose `owner-request`, then sealed to the owner's encryption key. Grant data is `event_digest, expected_epoch`. The owner validates the signed request, current membership, fresh nonce and time bound. The owner key stays in its encrypted local database with an external key, never at the relay. Owner requests/responses travel through opaque relay mailboxes.

Owner response: `schema, room, nonce, result`, signed with purpose `owner-response`, then sealed to the requesting peer. Grant result: `schema, room, sender, challenge, event_digest, expected_epoch, epoch, roster, issued, max_validity_seconds`. The roster includes room public keys/aliases and opaque write routes, not private records. The owner persists consumed challenge, membership transition, response bytes and cursor together. Exact request retries reuse response ciphertext and packet ID; a changed request under the same nonce is rejected.

Draft: `schema_version, room_id, event_id, author_room_key, author_sequence, previous_author_event, parent_event_ids, object_id, operation, payload`. Only `category, title, text` are projected from explicit user-composed cards. Private databases are never replicated. Persisted drafts and parent IDs are revalidated before requesting a grant; arbitrary extra fields fail closed. This prevents automatic private-field inclusion, not a user deliberately typing identifying text.

Delivery: `schema_version, draft, membership_epoch, recipient_set_digest, grant`, signed with purpose `delivery`, then sealed separately to each current recipient. The embedded owner response binds the exact draft digest and roster. Recipients verify sender signature, owner signature, bindings, membership, sequence and parents. Event IDs deduplicate; conflicting author sequences reject; missing-parent buffering is bounded; concurrent object heads remain separate until an explicit merge revision names their parents.

The sender uses a fresh random challenge per attempt and a monotonic deadline of at most 30 seconds. Grants are live only in the requesting process, tied to exact request/response bytes and start time. Beginning a batch consumes the grant once. The encrypted local attempt journal saves the exact ciphertext fanout and consumption before the first POST. A bounded retry repeats the same ciphertext and packet ID; it does not create a new envelope. Each POST checks the live grant and locally known epoch. Expiry, restart or known epoch change requires a new grant and recipient selection. A journal left after a crash never restores grant authority. Reprojection retains the immutable draft/event ID so recipients deduplicate partial delivery.

The owner must be online for new grants. Otherwise the UI reports `Room owner offline: saved locally, sync queued`. Removal blocks new grants and invalidates pending invitations. An already-issued grant may disclose its exact in-flight batch within its bounded window; local clients cannot instantly learn a remote removal. Prior ciphertext/plaintext remains readable to prior recipients. Historical delivery is accepted for offline catch-up using its embedded signed grant; the protocol cannot prove the actual original send time against a malicious authorized endpoint. Relay withholding/censorship reduces availability. These are explicit limitations, not instantaneous revocation or recall guarantees.

Collaboration remote transport permits only valid Tor v3 onion endpoints via localhost SOCKS5h. Environment proxies and redirects are disabled; failure has no direct fallback. Public research uses a separate approved-public-HTTPS profile through SOCKS5h, never room/private queries. Loopback transport exists only for explicit isolated software tests and is not anonymous. No Tor service is provisioned by the application. Live Tor/IP-leak verification has not been performed.

Resource bounds include eight room members, bounded JSON, 64 queued cards, 2,000 accepted events, 32 missing-parent events, finite relay storage and bounded retries. Capacity failure must be surfaced rather than silently deleting records. This candidate remains subject to independent code review and final integrated tests.

Revision 02 defensive changes: the entire queued outbox is validated before the first transport poll, including entries beyond the next send batch, and revalidated before grants. Inbound intrinsic chain rules are checked before insertion. Persisted pending entries are processed individually at startup and before receive admission; invalid entries are removed and counted as quarantined without reserving their sequence or stopping independent entries. Unknown valid dependencies remain bounded pending, and each known dependency is checked even if another is missing. These repairs have builder regression coverage; independent follow-up validation is incomplete and blocked, so no independent security pass is claimed.
